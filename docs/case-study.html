1痛点 · Pain Points （課題）

  • 需求 → 设计 → 测试链路长，靠邮件/口头传递，口径不一致、追溯困难。
  • 设计审查依赖资深工程师经验，新人漏检多、规则不沉淀。
  • 评价/测试清单每次从零开始，知识散落个人，项目结束即流失。
  • 知识库「只进不出」，没有闭环复用。
要件→設計→テストの流れが属人化し、レビューは熟練者の経験頼み。知識が蓄積・再利用されない。

2我搭了什么 · What I Built （構築したもの）

IntDevTools —— 研发集成开发工作台（11 个 Flask 服务），把研发活动串成一条可复用主线：

层组件
入口门户（3D 关系图 · 配置驱动 · 点击启动工具）
核心工具需求管理（V 型左半 + 追溯矩阵）· 设计审查（AI）· 评价基准生成（AI）· 文件版本与承认 · 计划生成 · 进度管理
基础设施统一认证（JWT）· 跨工具数据总线（禁止工具直连）· 工作流引擎 / 监控（预留）

公开演示聚焦 3 个核心工具做轻量化呈现（纯静态、可双击打开、可部署 GitHub Pages）。

3AI 用在哪 · Where AI Is Used （AI の役割）

环节AI 做什么人工确认
需求导入匹配示例标准 · 建议验证条目 · 判定开发等级（L1–L5）✔ 确认后写入
设计审查规则 + 知识库预审，输出发现（高/中/低）+ 置信度✔ 逐条采纳/忽略
评价基准按产品大类生成评价/测试清单（必须/推荐/参考）✔ 确认后流转
知识沉淀将已确认的审查经验提炼为可复用知识条目✔ 确认后入库
诚实口径：AI 是辅助 / 编排（human-in-the-loop），不是"AI 全自动"——每个 AI 结果都必须人工确认后才生效。
AIはオーケストレーション／アシスト。すべてのAI出力は人間の確認を経てから反映される。
